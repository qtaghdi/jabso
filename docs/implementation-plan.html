Jabso
Implementation Plan

앱이 내는 잡소리에서 원인을 찾는 개인용 오류 관측 도구. 오류 수집과 issue grouping을 먼저 완성하고, 같은 도메인 서비스를 UI와 MCP가 공유한다.

작성일 2026-08-21
Status: proposed
Scope: MVP → MCP

Context — 왜 지금?

이미 증명된 것

Sentry Browser SDK의 envelope를 자체 Next.js endpoint에서 받고, event 및 zlib replay segment를 byte 단위로 해제할 수 있다. 현재 fixture에는 동일 replay의 segment 0–7과 총 106개 rrweb event가 있다.

아직 제품이 아닌 이유

데이터가 로컬 파일에 저장되고 인증·quota·grouping·검색이 없다. Replay 마스킹도 꺼져 있어 현재 코드는 protocol spike로만 취급해야 한다.

제품 정의: Sentry 전체 대체가 아니라 개인 프로젝트를 위한 error inbox + issue grouping + MCP context. DOM Replay와 자체 browser SDK는 후순위다.

Phase 0스파이크 보존과 기반 정리

  • 현재 Next.js spike를 새 Jabso 저장소로 이전
  • 민감정보를 제거한 최소 envelope fixture 선별
  • parser를 fixture 기반 golden test로 고정
  • pnpm workspace와 Turborepo 초기화
  • Next.js 16으로 올리고 보안 audit 재확인
  • Boundra 버전을 exact pin하고 boundary check를 CI에 추가

Exit criteria: clean install, typecheck, build, parser tests, boundary checks가 새 환경에서 모두 통과한다.

P0Boundra 자체 오류 기록

재귀 방지 설계: Boundra runtime/adapter 오류는 일반 Jabso ingestion과 failing contract를 통과하지 않는다. 최소 diagnostic sink가 safe shape를 직접 기록하며 nested attempt는 recursion guard로 차단한다.

Primary sink

internal_diagnostics 테이블에 최소 repository 또는 SQL adapter로 직접 기록한다. 일반 issue count, quota, alert와 완전히 분리한다.

Fallback

로컬 개발에서는 .jabso-diagnostics/boundra.ndjson로 fallback한다. production에서는 선택한 배포 환경에 맞는 별도 durable fallback을 결정한다.

  • 기록: stable code, safe message, field path, contract name, operation, Boundra/Jabso version
  • 금지: original input, token, cookie, authorization header, 임의 환경 변수
  • CI boundary violation은 check-boundaries --format json artifact로 먼저 보존

Critical files

재사용 — 현재 스파이크에서 가져올 것
  • byte-level envelope parser
  • content encoding 처리의 성공 fixture
  • Sentry DSN을 자체 endpoint로 연결한 demo
  • Replay segment decoder는 별도 spike로 보존하되 MVP runtime에서는 제외
폐기 또는 격리
  • 인증 없는 /api/dumps는 production 코드로 승격하지 않는다.
  • 동기식 local filesystem persistence는 fixture/dev 전용으로만 남긴다.
  • Replay의 maskAllText: false, maskAllInputs: false는 demo 외부에서 사용하지 않는다.

Story 검증

  1. demo app에서 같은 오류를 세 번 전송
  2. 하나의 issue에 occurrence 3개가 쌓이는지 확인
  3. release가 바뀐 뒤 regression 표시 확인
  4. MCP로 issue 검색과 stack trace 조회
  5. 민감한 입력이 어떤 응답에도 없는지 확인

Out of scope

  • 다중 조직 billing과 복잡한 RBAC
  • Elasticsearch/ClickHouse의 선제 도입
  • MCP 쓰기 도구와 자동 issue 해결
  • Sentry protocol의 모든 item type 지원
